# Research: Costume Contest

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-10-20

Stack constraints from the user: Node + TypeScript, Next.js frontend, Express backend,
PostgreSQL, containerized for a single Docker host, peak load about 350 students on one night.
Redis only if needed.

## 1. Process layout: one Express server that mounts Next.js

- **Decision**: A single Node process. Express owns `/api/*`, and every other route is handed
  to Next.js through its request handler (a Next.js custom server). One container image.
- **Rationale**: Constitution IX requires one deployable unit. One process also means one
  origin, so the pass cookie is first-party with no CORS, and contest state can be cached in
  memory without a shared cache. It still gives a clear Next.js frontend and Express backend split
  in the code.
- **Alternatives considered**: Separate `web` and `api` containers behind a proxy. This means two
  images, cross-service config, and a shared cache to keep state in sync, and buys nothing at
  this scale. Next.js route handlers only, with no Express, was rejected because the user asked
  for Express.

## 2. Redis: not used

- **Decision**: No Redis. Read and write PostgreSQL directly, plus a small in-process cache of
  the public contest state.
- **Rationale**: At peak, 350 phones each poll every 4 s, which is about 90 requests/s of a
  sub-1 KB JSON payload. The public state (stage, reveal step, entry list version, rehearsal flag)
  changes only on crew actions, so it is held in memory and invalidated when a crew action
  writes. Most polls never touch the database, and 304 responses keep them tiny. Votes peak at a
  few hundred within a few minutes, which is trivial for PostgreSQL. With a single process there
  is nothing to share a cache between.
- **Alternatives considered**: Redis for state and rate limiting. It adds a container, a failure
  mode, and config for no measurable gain at this scale. Revisit only if the app runs more than
  one process.

## 3. Student updates: polling with ETags

- **Decision**: Students poll `GET /api/state` every 4 s with ±1 s jitter and `If-None-Match`.
  Crew and the big screen poll every 2 s. On errors, polling backs off up to 20 s and resets on
  success. Polling pauses while the tab is hidden.
- **Rationale**: Constitution III prefers polling over long-lived connections on student phones.
  A 4 s interval plus jitter meets SC-004 (crew action visible within 5 s on phones) on average;
  the big screen at 2 s meets it reliably.
- **Alternatives considered**: SSE or WebSockets, which the constitution rules out for student
  phones, and which handle wifi drops poorly.

## 4. Data access: Drizzle ORM with drizzle-kit migrations

- **Decision**: `drizzle-orm` with the `pg` driver, schema in TypeScript, and SQL migrations
  generated by `drizzle-kit` and applied on container start.
- **Rationale**: Typed queries that stay close to SQL. One-vote and uniqueness rules can be
  expressed as real database constraints (partial unique indexes) and transactions, which is
  what Principle V needs, and migrations are plain SQL files.
- **Alternatives considered**: Prisma (heavier runtime engine and weaker support for partial
  indexes); Kysely (also fine, but has no schema-to-migration generator); raw `pg` (no types).

## 5. Identity, sessions, and the big-screen link

- **Decision**:
  - **Pass**: a 32-byte random token in an `HttpOnly; Secure; SameSite=Lax` first-party cookie,
    stored only as a SHA-256 hash. Live and rehearsal passes use separate cookie names
    (`np_live`, `np_rehearsal`) so turning rehearsal off brings back the live pass.
  - **Crew**: `POST /api/crew/session` with the shared passcode (`CREW_PASSCODE` env) and a
    device label returns a signed session cookie (12 h). Failed attempts are rate-limited per IP
    in memory, with an increasing delay after 5 failures.
  - **Big screen**: the crew dashboard shows a link containing `SCREEN_TOKEN` (env). Opening it
    sets a read-only screen cookie.
- **Rationale**: Meets Principle II (cookie only, no accounts). Hashing the token means a
  database leak cannot be used to impersonate passes. An in-memory rate limiter is enough for a
  single process.
- **Alternatives considered**: localStorage identity, which is not sent with image requests and
  so would break pass-gated photo URLs. JWTs add nothing over signed cookies here.

## 6. Photos: client resize, server re-encode, private disk volume

- **Decision**: The crew device captures with `<input type="file" accept="image/*"
  capture="environment">`. If camera access is refused, the same input falls back to the photo
  library. The browser resizes to at most 1600 px on the long edge and JPEG quality 0.8 using a
  canvas before upload. The server accepts up to 3 MB (multer, memory storage) and uses `sharp`
  to re-encode two WebP files: 1200 px (about 120 KB) and a 480 px thumbnail (about 25 KB).
  All metadata, including EXIF GPS, is stripped. Files are written to a private Docker volume
  under random names. They are served only through `GET /api/photos/:photoId/:size`, which checks
  for a pass, crew, or screen cookie and responds with `Cache-Control: private, max-age=86400,
  immutable`.
- **Rationale**: Principle III (small uploads and payloads) and Principle I (no public URLs, no
  location metadata about minors). Re-encoding on the server guarantees stripped metadata even
  if the client resize is skipped. With about 60 entries, the gallery is about 1.5 MB of
  thumbnails per phone, fetched once.
- **Alternatives considered**: Storing photos in PostgreSQL (bloats the database and backups);
  object storage such as S3 (an extra service, and signed URLs are still public URLs while they
  last).

## 7. Concurrency and idempotency

- **Decision**:
  - Every crew mutation and every vote carries an `Idempotency-Key` header (a UUID generated
    when the action starts). Keys are stored with the response for 24 h, and a repeated key
    replays the stored response.
  - Votes are additionally protected by a partial unique index: at most one non-released vote per
    pass.
  - Stage changes send the expected current stage. A mismatch returns `409` with the current
    state, so two crew devices acting at once resolve in order.
- **Rationale**: Principle III (safe retry) and Principle V (enforced on the server). The database
  constraint is the last line of defence even if idempotency handling has a bug.
- **Alternatives considered**: Client-side disabling only, which breaks on retries and the back
  button.

## 8. Rehearsal isolation: a `realm` column

- **Decision**: Every row in passes, entries, votes, contest, and audit carries
  `realm ∈ {live, rehearsal}`. A singleton settings row holds `rehearsal_mode`. Requests act on
  the active realm. Wipe is `DELETE … WHERE realm = 'rehearsal'`, deletes rehearsal photo files,
  and resets the rehearsal contest row to setup. Rehearsal mode cannot be turned on once the live
  contest has left setup.
- **Rationale**: Principle VII (dry run plus wipe without touching live data). Keeping the two
  realms in the same tables means the rehearsal exercises exactly the same code paths.
  Uniqueness constraints are per realm, which satisfies FR-002's separate nickname space.
- **Alternatives considered**: A second database or schema. That would need a connection switch
  and duplicated migrations, and the rehearsal would no longer test the real setup.

## 9. Photo and data deletion

- **Decision**: `PHOTO_DELETE_AT` (env, default `2026-11-02T00:00:00-07:00`). After that time,
  photo requests return 410 and the app runs the purge hourly. A purge script
  (`npm run purge -- --all`) deletes photo files and wipes all tables. It is documented as the
  data-deletion procedure, alongside `docker compose down -v` to remove the volumes. No automated
  database backups are taken.
- **Rationale**: FR-040 and Constitution IX. The time-based purge is deletion, not a contest stage
  change, so it does not conflict with Principle VI. The manual script covers the case where the
  server is stopped before the purge date.
- **Alternatives considered**: Cron in a separate container, which is an extra moving part.

## 10. Front end

- **Decision**: Next.js App Router with React. Student, crew, and screen views are client
  components that poll the API, and pages are statically rendered shells. Styling uses CSS
  Modules with design tokens as CSS custom properties: dark purple `#1a0b2e` background,
  pumpkin `#ff7a1a` accent, and text colors checked to WCAG AA. Fonts are loaded with
  `next/font/google`, which self-hosts them at build time, so no request goes to Google at
  runtime: Creepster for headings and Nunito for body text. QR codes are rendered as SVG on the
  server with `qrcode`.
- **Rationale**: Principles I and VIII. There are no third-party requests at runtime, and only a
  small amount of client JS beyond React and Next.
- **Alternatives considered**: Tailwind, which works but adds build config for a handful of
  screens. A component library, which adds weight and has its own contrast defaults to fight.

## 11. Testing

- **Decision**:
  - Vitest for unit tests: state machine, ranking, nickname generation.
  - Vitest + Supertest integration tests against a real PostgreSQL started with
    `docker compose -f compose.test.yml` for vote enforcement, photo access, idempotency, and
    rehearsal wipe.
  - Playwright end-to-end smoke tests on iPhone and Pixel device profiles in WebKit and Chromium.
  - An `autocannon` load script that simulates 400 polling clients plus a burst of 350 votes.
- **Rationale**: Principle VII names vote enforcement, the state machine, and photo handling.
  Those must be tested against the real database constraints, not mocks. SC-005 needs an actual
  load check.
- **Alternatives considered**: Jest (slower with TypeScript and ESM); k6 (a separate binary,
  while autocannon is just an npm dependency).

## 12. Hosting and TLS

- **Decision**: Docker Compose on one Linux VPS with three services: `app`, `db`
  (postgres:17-alpine), and `caddy` (automatic HTTPS for the event domain). Deploy with
  `./scripts/deploy.sh`, which runs `docker compose up -d --build` and then a health check.
- **Rationale**: Principle IX (one deployable app unit, environment config, one command). Caddy
  handles certificates with no manual steps. HTTPS is required for `Secure` cookies and camera
  access.
- **Alternatives considered**: Hosting on the church LAN, which needs local DNS and certificates
  and doesn't help phones on cellular. A managed platform, which the user did not ask for.

## Versions

Node.js 24 LTS, TypeScript 5.x, Next.js 16, React 19, Express 5, PostgreSQL 17, Drizzle ORM
(latest), sharp (latest), Vitest 3, Playwright (latest). Exact versions are pinned in
`package.json` and the lockfile during implementation.
